ai-memory: 에이전트끼리 기억을 잇는 AI 코딩 장기 기억 오픈소스, 받아서 돌려 봤다

한 줄 요약

AI 코딩 에이전트끼리 작업 기록을 나눠 갖게 해 주는 Rust 기반 오픈소스 ai-memory를 내려받아, 설치 없이 인터넷 없이 의존성이 없는 shell 훅 레이어만 실험해 본 기록입니다. 서버 바이너리 실행, MCP, 검색, 기억 통합(consolidation)은 확인하지 못했습니다.

무엇인가

ai-memory는 AI 코딩 에이전트용 장기 기억 도구입니다. Claude Code를 중간에 껐다가 같은 디렉토리로 OpenAI Codex를 열면, 아키텍처·실패한 접근·아직 남은 질문을 다시 설명하지 않고 이어갈 수 있게 합니다. 단일 Rust 바이너리로 MCP 서버와 라이프사이클 훅을 함께 제공합니다(MIT 라이선스, GitHub star 10,407 / fork 747, 2026-05-21 생성 — 2026-10-19 기준).

README가 설명하는 흐름은 네 단계입니다.

capture ──▶ consolidate ──▶ recall ──▶ handoff
 hooks        session-end      search     next agent,
 observe      summaries as     + brief    any harness
 silently     wiki pages       injection
  • capture: 에이전트 라이프사이클 훅이 세션 중 관찰(prompt, 툴 호출, 세션 경계)을 조용히 기록하고, 저장 전에 타입이 정의된 프라이버시 경계에서 세니타이즈(크기·secret 경계)합니다.
  • consolidate: 세션 종료 시 관찰을 가독성 있는 markdown 페이지로 컴파일합니다. 데이터 원본은 git 기반 위키(일반 .md 파일)이고, SQLite 데이터베이스는 언제든 파일로부터 재건할 수 있는 파생 인덱스에 불과합니다.
  • recall: 다음 세션에서는 어떤 에이전트에서도 제한된 분량의 브리핑을 주입받고, 전체 텍스트(FTS5)·엔티티·링크를 하나의 랭킹으로 융합해 검색합니다.
  • handoff: 에이전트 간 인계는 소유자가 있고 딱 한 번만 접수되는 타입 정의 프로토콜로 명시적으로 이어집니다.

README가 강조하는 특징은 몇 가지입니다. 20개 이상의 harness(Claude Code, Codex, Cursor, Gemini CLI, Grok, Kimi, Kiro 등)가 하나의 공유 기억에 연결됩니다. 기본 경로는 LLM 호출이 전혀 없으며, API 키 없이 캡처·검색·handoff·감쇠(decay)가 동작합니다. LLM 통합, 벡터 검색, "dream" 재작성 같은 기능은 전부 opt-in이며 기본 꺼짐 상태입니다. 기억은 사용자가 직접 실행하는 서버(같은 노트북, homelab 박스, 어딘가)에 저장되어 기계·프로젝트·사람을 초월해 따라옵니다. README는 쓰기가 대략 초당 700회 수준으로 측정되었고, purge 명령은 "삭제"가 정확히 무엇인지를 명시한다고도 합니다.

설치는 README 기준으로 두 명령입니다.

curl -fsSL https://github.com/akitaonrails/ai-memory/releases/latest/download/install.sh | sh
ai-memory setup

install.sh는 OS/CPU에 맞는 릴리스를 받아 공개 SHA-256으로 검증하고(맞지 않으면 설치를 거부), ~/.local/bin/ai-memory로 링크합니다. ai-memory setup은 데이터 디렉토리와 owner-only 파일의 bearer 토큰을 만들고, 사용자 단위 systemd/launchd 서비스를 시작하며, 발견한 에이전트에 MCP·훅·Agent Skills를 연결합니다.

직접 해 본 것

저는 이 저장소를 받아 설치는 하지 않았습니다. 실험 환경은 인터넷에 차단된 로컬망 전용 환경이었고, cargo/rustc가 없어서 Rust 서버 바이너리를 빌드하고 실행하는 것은 불가능했습니다. 그래서 의존성이 없는 shell 훅 레이어만 실행했습니다.

훅 테스트 슈트를 셸별로 돌려 봤습니다.

/bin/sh tests/hooks/test_lib.sh
/bin/dash tests/hooks/test_lib.sh
bash tests/hooks/test_lib.sh
zsh tests/hooks/test_lib.sh
  • macOS 기본 /bin/sh(bash 3.2): 211 passed, 8 failed. 8개 실패는 전부 multi-line case가 $(...) 명령대체 안에 있어 bash 3.2 구문 분석이 깨진 것입니다(출력: syntax error near unexpected token 'newline'). 훅 로직 실패가 아니라 내 셸 버전 문제입니다.
  • /bin/dash: 219 passed, 0 failed. CI의 POSIX shell 기준으로 훅 스크립트 자체는 정상입니다.
  • bash: 211 passed, 8 failed (동일한 bash 3.2 문제).
  • zsh: aliases: attempt to set slice of associative array로 중단(테스트는 bash/dash 계열을 가정한 것).

설치 스크립트 테스트도 돌렸습니다.

bash tests/install_sh.sh

통과했습니다("install.sh checks passed" — symlink/hardlink 거부, sha256, file:// URL 기반. 네트워크 불필요).

훅과 서버 사이의 E2E도 한 번 돌려 봤습니다. python3 표준 라이브러리만으로 HTTP 스텁 서버를 만들어 localhost로 띄우고 훅을 붙였습니다. 스텁에 응답 버그가 있어 1회차 실행은 POST 500으로, 훅이 spool에 쌓기까지를 관찰했습니다. spooldata/hook-spool/*.json 2개에, URL 필드에 .ai-memory.toml 마커가 해석된 workspace/project 값과 ingest_key가 실제로 붙는 것을 확인했습니다. 훅 stdout은 {}를 반환했고(클라이언트 로그는 깨끗했습니다). 버그 수정 후 새 디렉토리에서 재실행하려 했으나 스텁 프로세스가 120초 자동 종료로 이미 죽어 있어 2회 실험은 하지 못했습니다. 유효 결과는 1회 실행뿐입니다.

확인하지 못한 것(솔직히):

  • Rust 서버(serve) 실행 — cargo 부재 + 인터넷 차단.
  • MCP 도구 호출, 검색, consolidation — 서버 바이너리 없이는 불가.
  • install.sh의 릴리스 자산 다운로드 경로 — 인터넷 차단. 오프라인 file:// 분기만 검증.

이 맥에서 쓸 수 있나

제가 이 글을 쓴 환경은 Mac Studio(M5 Max, 메모리 48GB)이며, 로컬 AI 모델 서버가 메모리 약 34GB를 상시 사용합니다. 이 환경 기준으로, 위 실험과 README·라이선스 근거만 놓고 보면:

  • zero-LLM 모드만 쓴다면: LLM 제공사 API 의존이 없습니다. 서버가 우리가 띄우는 localhost에 데이터가 저장되므로 세션 관찰 데이터의 저장 위치는 우리가 통제할 수 있어, 이 부분은 이 환경에서 쓰는 데 부담이 작습니다.
  • LLM 기능(consolidation, dream, 임베딩)을 켜면: Anthropic/OpenAI/Gemini 등 외부 제공사 API로 세션 요약 텍스트가 나가는 경로가 생깁니다. 이 맥에서는 모델 서버가 34GB를 상시 쓰므로, LLM 통합을 켜는 순간 메모리·비용 부담이 겹칩니다. 이 기능은 기본 꺼져 있으므로, 안 켜면 이 부담은 없습니다.
  • 메모리: 서버는 SQLite+스윕+git 커밋을 돌리는 데몬인데, 이 모델 서버(약 34GB)가 점유하는 환경에서 데몬이 추가적으로 얼마나 차지하는지는 실측하지 못했습니다.

이런 분께

  • Claude Code, Codex, Cursor 같은 여러 AI 코딩 에이전트를 오가며 쓰고, "이 프로젝트 왜 이렇게 했지, 무엇이 아직 안 됐지"를 매번 다시 설명하는 게 귀찮은 분.
  • 기억을 git 기반 markdown 위키(일반 .md 파일)로 갖고, grep으로 뒤지고, Obsidian으로 열고, 손으로 고치고 싶은 분.
  • 기본은 LLM 없이(내 데이터가 제 서버에) 돌리되, 필요할 때만 LLM 통합을 켤 수 있는 "선택적" 구조가 좋은 분.
  • 팀 단위로 한 서버를 공유하고, 세션 학습을 모두의 에이전트가 검색하도록 하고 싶은 분.

주의할 점

  • 프롬프트 인젝션 표면: 훅이 가져온 세션 관찰·메모리는 "신뢰할 수 없는 과거 데이터"로 다뤄야 합니다. 이 도구의 내부 문서도 검색해 온 기억을 명령으로 쓰지 말라고 명시합니다. 이 도구가 sanitize하는 것은 크기와 secret 경계일 뿐이며, README 자체가 "저장된 문구를 신뢰하게 만들 수는 없다(Sanitization... cannot make stored prose trusted)"고 합니다. 위키 페이지를 에이전트 문맥에 주입하면 악성 콘텐츠가 기억으로 영구화될 수 있습니다.
  • 데이터 유출 경로: 훅은 세션 관찰을 HTTP로 서버에 POST합니다. 서버가 우리가 띄우는 localhost라면 통제 가능하지만, 훅을 실제로 붙이는 순간(클로드/커서 등) 모든 세션 관찰이 그 서버로 흐릅니다. 서버 포트·인증(레포의 docs/users.md에 4단계 인증을 다룸)·반출 백업 정책을 먼저 정해야 합니다.
  • LLM 기능을 켜면 제3자 API로 세션 요약 텍스트가 나가는 경로가 생깁니다. 개인적 데이터가 있는 세션을 LLM 통합에 넘기면 제공사 사용 조건 문제가 됩니다.
  • bash 3.2 호환성 공백: 이 실험 환경의 POSIX 테스트 슈트가 8건 실패 — bash 3.2 구문 문제. 훅이 bash 3.2 환경에서 깨질 수 있다는 신호입니다(CI 기준은 통과). 실제로 훅을 bash로 실행하는 클라이언트가 이 머신에서 bash 3.2를 쓰면 마커 해석이 깨질 수 있습니다. 실제 클라이언트 테스트는 하지 못했습니다.
