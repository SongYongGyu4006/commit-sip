AI 글의 지어 낸 숫자를 잡는 numguard, 설치 없이 직접 돌려 봤다

2026년 10월 29일 · 읽는 데 5분
한 줄 요약AI가 자료를 보고 쓴 글에서 숫자·이메일·URL이 정말 자료에 나오는지 모델 없이 대조해 주는 Python 도구 numguard를 받아 봤다. 설치하지 않고 로컬에서 코드를 읽고 돌려 본 기록이다.

무엇인가

numguard는 LLM이 쓴 초안(보고서·블로그·대본·발표자료)을 검사한다. 숫자, 이메일/URL, 그리고 한국어 글에 섞여 들어온 한자·가나를 찾아서 주어진 자료에 없는 것을 알려 준다. 모델도 의존성도 없이 정규식으로 찾아 맞춰 보기만 해서 가볍다.

주요 동작은 이렇다.

  • 숫자 표기를 하나로 맞춰 읽는다. 4,350,000, 0.55, -0.57% 같은 숫자뿐 아니라 435만, 1억 2,000만, $816 B처럼 단위가 붙은 표기도 같은 값으로 본다.
  • 한글로 쓴 숫자도 읽는다. 구십구만 사천삼백십원은 994,310으로 읽고, 이천육백오십오, 세 개, 열흘도 알아본다.
  • 계산값은 따로 표시한다. 자료에 있는 두 숫자의 합·차·비율·퍼센트는 derived(계산값)로 나온다. 기본 모드에서는 통과시키고, --strict를 주면 실패로 처리한다.
  • 근사는 approx로 표시한다. 예를 들어 약 99만 원이 994,310에 가까우면 근사로 인정한다.
  • 이메일·URL은 반드시 자료에 있어야 한다. 없으면 NOT FOUND다.
  • 에이전트 기억 파일을 주면(옵션) 그 파일에만 있는 단어가 글에 새어 들어간 "기억 누수"도 잡는다.

라이선스는 MIT, 언어는 Python이다. GitHub 별과 포크는 0개, 2026-10-29에 만들어진 새 저장소다.

직접 해 본 것

저장소를 받아 설치 없이(인터넷도 끊긴 채로) 로컬에서 코드를 읽고, 실행할 수 있는 것만 돌렸다. 실행은 python3 -m numguard로 한다.

동봉된 테스트 22개는 모두 통과했다.

$ cd project/repo && python3 -m unittest discover tests
Ran 22 tests in 0.010s — OK

한글 숫자, 단위(억/만/B), 계산값, 이메일, 한자 섞임, 메모리 누수, 근사, 리스트 마커, 반올림까지 다룬다.

합성 초안 검사. 일부러 문제를 심어 둔 초안과 자료로 검사했다.

$ python3 -m numguard check ../trial/draft.md --source ../trial/facts.md
checked 8 · grounded 4 · not found 5   → FAIL, EXIT=1

심어 둔 255원(지어 낸 값), 60%(지어 낸 값), someone@uni.ac.kr(지어 낸 값), 한국어 문장에 섞여 들어간 중국어 글자를 정확히 잡았다. 구십구만 사천삼백십원=994,310은 통과했고, 2,655원은 derived (1,000,000-997,345)로 표시됐다. README 예시와 같은 결과다.

버그 1건. 이메일 바로 뒤에 조사가 붙으면 오탐이 난다. lab@example.org로에서 정규식이 조사 로까지 같이 잡는 바람에 문자열이 달라져 "NOT FOUND"가 뜬다. 마침표(.)나 공백이 뒤따를 때는 정상이었다. 실제 문서에 "문의: ...@...로" 같은 패턴은 드물어서 심각하진 않다. 다만 고치지 않고 쓰면 이 경우엔 오탐이 난다.

메모리 누수 확인. --memory 옵션으로 기억 파일을 주니, 자료에 없는 포스코아카데미·우수상을 "기억 단어"로 잡았다.

strict·JSON 확인. --strict --json으로 돌리면 계산값(2,655)도 NOT FOUND로 올라가고, 에이전트가 파싱하기 좋은 JSON 스키마가 제대로 출력됐다.

여기 적은 건 직접 해 본 것뿐이다. pip install 설치와 PyPI 배포 상태는 확인하지 않았다.

이 맥에서 쓸 수 있나

실험 환경은 Mac Studio, Apple M5 Max, 메모리 48GB, macOS 27.0.1(빌드 26A434), 디스크 여유 약 156GB다. 여기에 메모리를 상시 약 34GB 쓰는 로컬 AI 모델 서버가 돌고 있다.

numguard는 모델 없이 정규식만 돌리기 때문에 칩이나 메모리 사양을 따질 필요가 없다. 읽을 파일이 클 때 CPU와 메모리를 조금 더 쓰는 정도다. 48GB 메모리에서 실험도 가볍게 돌았고, 로컬 AI 서버가 34GB를 쓰고 있어도 별 영향이 없었다. 이 맥에서 쓰는 데 걸릴 건 없다.

이런 분께

잘 맞는 경우:

  • AI로 보고서를 많이 만들고, 발표 전에 "자료에 없는 숫자가 슬쩍 끼어들지 않았나"를 기계로 한 번 더 확인하고 싶은 사람
  • 블로그·쇼츠 대본처럼 숫자를 소리 내어 읽는 글을 만들면서, 녹음이나 출력 전에 사실 확인 단계를 넣고 싶은 사람
  • 의존성 없이 가볍고, 한국어 숫자 표기까지 챙기는 검사가 필요한 경우

맞지 않는 경우:

  • "문맥상 같은 값인지"까지 판단해 주길 바라는 사람. 지어 낸 값이 우연히 자료의 다른 곳에 있으면 못 잡는다. README 기준 실측에서 지어 낸 숫자 42개 중 27개(71%)만 잡았다. 문맥 매칭은 아직 없다.
  • 이메일 뒤에 조사가 붙는 문장("...@...로")이 많은 문서에 바로 쓰려는 사람. 이 경우 오탐이 실제로 재현됐다.

주의할 점

  • 값만 찾아 맞춰 보는 방식이라 한계가 크다. 지어 낸 값이 자료의 다른 곳에 우연히 있으면 놓친다.
  • 이메일 오탐: 조사가 붙는 ...@...로 패턴에서 재현됐다.
  • 계산값(derived)은 기본 모드에서 통과한다. 계산 실수까지 잡으려면 --strict를 줘야 한다.
  • 코드 블록 안의 숫자는 기본적으로 검사하지 않는다(의도된 동작).
  • 버전이 0.1.0이라 아직 초기 단계다.
