repo-proof: 오픈소스 README 주장을 코드 판정으로 검증하는 도구, 직접 받아 돌려 본 기록

한 줄 요약repo-proof는 "이 저장소의 README가 실제로 맞는가"를 기계로 판정하는 도구다. 설치 없이 저장소만 받아서, 인터넷이 끊긴 환경에서 읽을 수 있는 부분만 읽었다. 그러다 판정 로직에서 다중 줄 정규식 결함 하나를 재현했다.

무엇인가

repo-proof에 GitHub 주소를 넣으면 그 도구가 README에 적은 핵심 주장을 실제로 증명하는지 점검한다. 과정은 다섯 단계다.

1) 대상 저장소를 격리된 폴더(샌드박스)로 가져와 필요한 설치물을 마련한다. 네트워크는 이 단계에서만 쓴다.
2) 계획 담당 AI가 README·파일 목록·소스 발췌 같은 텍스트만 읽고 시험 계획을 짠다. 실행은 하지 않는다.
3) 인터넷이 끊긴 격리 환경에서 시험을 실행하고 출력을 증거로 남긴다. 이때는 로컬 모델 서버에만 접속할 수 있다.
4) 계획을 잘못 짜서 실패했다면 계획의 명령만 한 번 고친다.
5) 통과·실패 판정은 AI가 아니라 코드가 내린다.

마지막 단계인 "판정은 코드가 한다"가 이 도구의 가장 큰 차별점이다. 보통 AI에게 "이거 써 보고 알려 줘"라고 하면 시험을 돌리는 것도, 채점하는 것도 그 AI다. 그러니 자화자찬이 되기 쉽다. repo-proof는 계획만 AI에게 맡기고 실행·증거·판정은 고정된 코드가 맡도록 나눠 놓았다.

코드는 많지 않다. 파이썬 파일 8개에 표준 라이브러리만 써서 따로 설치할 것이 없다. 라이선스는 MIT다.

직접 해 본 것

환경부터 적는다. Mac Studio M5 Max, 메모리 48GB, macOS 27.0.1이고, 로컬 AI 모델 서버가 메모리를 상시 약 34GB 쓰고 있었다. 그리고 이 환경은 인터넷이 막혀 있다. 이 점이 뒤에서 크게 작용한다.

저장소를 받고 자체 테스트부터 돌렸다.

python3 -m unittest discover -s tests

7개 모두 통과했다(0.001초). 판정·정규식·경로 처리 같은 로직에 단위 테스트가 실제로 있고, 그 테스트가 통과한다는 것까지 확인했다.

다음으로 CLI가 README에 적힌 옵션대로 뜨는지 봤다.

PYTHONPATH=. python3 -m repo_proof run --help

옵션 목록이 정상적으로 나왔고 README 내용과 같았다.

여기서부터는 솔직하게 적어야 할 부분이 있다. 이 도구의 전체 플로우(다른 저장소 검증)는 1단계에서 대상 저장소를 클론하므로 네트워크가 필요하다. 그래도 하나 시도해 봤다.

python3 -m repo_proof run https://github.com/torvalds/linux --no-sandbox

git clone이 실패했고(포트 443에 연결하지 못함) 판정은 "error"로 나왔다. 이 환경(인터넷 차단)에서는 전체 플로우를 돌릴 수 없다는 뜻이다. 도구의 결함이라기보다는, 도구가 설계상 설치 단계에서만 네트워크를 허용하다 보니 우리 시험 환경의 제약이 더 크게 작용한 결과다.

그래서 인터넷 없이 돌아가는 부분만 골라 실제로 돌려 봤다.

  1. 오프라인 판정·보고 흐름 — 계획 검증부터 판정, 결과, 보고서 생성까지 가짜 데이터로 한 바퀴 시뮬레이션했다. 계획 검증은 통과했고 보고서 파일(REPORT.md, report.json)도 정상적으로 만들어졌다. "판정은 코드가 한다"는 주장이 실제로 동작하는 것을 확인한 셈이다.
  2. 판정 로직의 정규식 결함 재현 — 판정기가 출력을 검사할 때 쓰는 정규식을 세 가지 케이스로 실험했다. 통과한 건 한 줄짜리 출력(ROWS=2)뿐이었다. 두 줄짜리 출력(그중 한 줄이 ROWS=2)은 두 줄의 순서를 바꿔 봐도 둘 다 실패였다. 원인은 소스를 읽고 특정할 수 있었다. 판정 로직이 "줄 단위로 매치" 옵션(여러 줄짜리 출력을 줄마다 처리하게 하는 정규식 옵션)을 켜 두지 않았다. 그래서 ^...$ 기준으로 쓴 시험은 출력이 두 줄 이상이면 줄의 첫·마지막에만 매치돼 거의 항상 잘못 실패한다. 실제 CLI는 대개 여러 줄을 출력하니, README가 권장하는 "측정 가능한 KEY=VALUE 줄을 정규식으로 확인" 방식은 현실에서 거의 항상 실패로 판정될 수 있다.

못 해 본 것: 다른 저장소를 실제로 검증하는 전체 실행(인터넷이 필요한데 차단돼 있어 불가), 샌드박스 격리 실행(설치하지 않음 — 시험 범위 밖), 계획 담당 AI가 실제로 시험 계획을 짜는 과정(로컬 모델을 호출해야 하지만 시험 범위 밖).

이 맥에서 쓸 수 있나

이 도구가 요구하는 조건과 맞춰 보면 된다. 계획·판정을 할 AI 모델은 로컬 서버(localhost)만 허용하므로 로컬에 모델 서버가 떠 있어야 한다. 샌드박스는 맥에서 sandbox-exec 프로필을 쓴다. 이 프로필이 ~/.ssh, ~/.config, ~/.aws 같은 비밀 디렉터리 읽기를 막고, 시험 중에는 외부 네트워크 대신 localhost만 허용한다는 점도 README에 적혀 있다.

이 맥의 사양을 그대로 옮기면 다음과 같다. Mac Studio, 칩 Apple M5 Max(arm64), 메모리 48GB, macOS 27.0.1(빌드 26A434), 디스크 여유 약 155GB, 로컬 AI 모델 서버(Splash 1.2.0)가 메모리 약 34GB를 상시 사용. 로컬 모델 서버가 있고 샌드박스도 이 맥의 sandbox-exec 방식이니, 도구가 요구하는 조건은 충족한다. 다만 모델 서버가 늘 약 34GB를 차지하고 있어서 시험 대상이 무거우면 남는 메모리 여유가 줄어든다.

판정 결함(위에서 재현한 정규식 문제)은 이 맥과 상관없이 그대로 남아 있다. 그러니 판정 결과만으로 결론을 내리기 전까지는, 사람이 출력을 한 번 더 확인하는 단계를 거치는 편이 안전하다.

이런 분께

맞아요:

  • "README에 적힌 기능이 실제로 되는가"를 기계로 확인하고 싶은 개발자
  • 로컬 AI 모델로 실험할 환경이 있는 사람
  • 판정 로직의 투명성(코드로 된 고정 규칙)을 중요하게 보는 사람

안 맞아요:

  • "설치하자마자 전체 플로우를 돌려 보고 싶다"는 사람 — 전체 플로우는 대상 저장소를 클론할 때 네트워크가 필요하다
  • 판정 결과를 그대로 믿어야 하는 용도 — 지금은 정규식 결함 때문에 다중 줄 출력이 잘못 실패할 수 있다
  • 이 환경에서 다른 저장소 검증까지 하려는 사람 — 인터넷 차단 환경에서는 전체 플로우를 돌릴 수 없다

주의할 점

  1. 판정 오판(재현 확인됨): ^...$ 기준으로 쓴 정규식은 출력이 두 줄 이상이면 거의 항상 실패로 판정된다. 실제로는 통과하는 시험이 "실패"로 나올 수 있다. 이 결함이 고쳐지기 전까지는 판정 결과만 믿지 말고, 사람이 출력을 확인하는 단계를 두어야 한다.
  2. 설치 단계 네트워크: 네트워크는 1단계(클론·설치)에서만 쓴다. --no-sandbox 옵션으로 격리 없이 돌리면 모르는 코드를 그대로 설치하고 실행하게 된다. 그래서 README에도 "신뢰하지 못하는 코드에는 쓰지 말라"고 적혀 있다.
  3. 계획의 질은 여전히 AI: 판정은 코드가 하지만 통과 기준은 AI가 쓴다. 기준이 엉터리면 판정도 엉터리다. README도 "판정은 계획이 쓴 기준만큼 좋다"고 스스로 경고한다.
  4. 시간·자원: 시험 1개당 기본 10분, 시험은 3개까지, 수정은 한 번까지다. 로컬 모델로 계획 AI를 돌리면 호출에 수십 초에서 분 단위가 걸린다.
  5. 이번 시험의 한계: 인터넷 차단 환경이라 전체 플로우(다른 저장소 검증)는 못 해 봤다. 위의 "직접 해 본 것"에는 이 환경에서 실제로 돌린 것만 적었고, 설치나 인터넷이 필요한 단계는 하지 못했다.
