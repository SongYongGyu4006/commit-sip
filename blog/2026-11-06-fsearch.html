fsearch, 오타가 나도 0.1ms 만에 파일 찾는 Mac용 검색 도구 — 받아서 돌려본 기록

2026년 11월 6일 · 읽는 데 4분
한 줄 요약macOS에서 디스크 전체의 파일을 검색하는 도구 fsearch를 저장소째 받아 설치하지 않은 채로 살펴봤습니다. 바이너리는 실행하지 못했고, 대신 예제 스크립트 3종을 돌렸습니다.

무엇인가

fsearch는 파일 이름과 파일 내용을 계속 추적하는 macOS용 검색 도구입니다. 디스크 전체는 처음에 한 번만 훑습니다. 그다음부터는 바뀐 파일만 약 15ms 안에 반영하기 때문에 인덱스가 늘 최신 상태로 유지됩니다.

이름 검색에서는 오타를 어느 정도 봐줍니다. mian.rs로 쳐도 main.rs가 나오고, 8글자 이상인 단어는 오타 두 개까지 허용합니다. 내용 검색은 미리 만들어 둔 인덱스로 후보를 먼저 좁히고, 그렇게 남은 파일만 실제로 열어서 읽습니다. 그래서 빠릅니다.

CLI 말고도 코딩 에이전트에 붙여 쓰는 MCP 서버가 함께 들어 있습니다. MCP는 AI 에이전트가 외부 도구를 호출할 때 쓰는 표준 규격입니다. 이 서버가 제공하는 도구는 파일 찾기, 내용 검색, 여러 파일 동시 검색입니다.

라이선스는 MIT입니다. 저작권만 표기하면 상업적으로 쓰거나 재배포해도 됩니다.

직접 해 본 것

저장소를 받은 뒤 인터넷을 끊은 상태에서 살펴봤습니다. 이 Mac에는 Rust 컴파일 도구가 없었습니다. which cargo rustc로 확인했고, Homebrew로 설치된 목록에도 없었습니다. 바이너리를 쓰려면 릴리스에서 받아 설치해야 합니다. 하지만 이번 시험은 설치를 허용하지 않았기 때문에 바이너리, 데몬, MCP 서버를 실제로 띄워 보지는 못했습니다.

대신 예제로 들어 있는 Python 스크립트 3종을 돌렸습니다.

첫 번째 스크립트로는 제가 만든 dummy git 저장소(22개 파일)에서 테스트용 질문을 뽑았습니다. n=8로 올리면 "Sample larger than population" 에러가 납니다. 이름이 겹치지 않는 파일이 8개가 안 돼서 나는 에러라 정상 동작으로 봤습니다.

두 번째 스크립트는 그렇게 만든 질문 묶음의 통계를 냈고, 세 번째 스크립트는 실행 결과 두 개를 나란히 비교하는 표를 만들었습니다. 세 개 모두 종료 코드 0으로 끝났고, 명령을 어떤 형식으로 넣어야 하는지와 출력이 어떤 형식으로 나오는지도 직접 확인했습니다. 다만 비교 표의 숫자(예: top1 100.0 → 92.0)는 제가 임의로 만든 데이터에서 나온 값이라 실제 성능과는 관계가 없습니다.

네 번째 예제는 바이너리 두 개를 맞붙이는 스크립트입니다. 컴파일된 바이너리 경로를 인자로 줘야 하는데 바이너리가 없어서 실행하지 못했습니다.

$ which cargo rustc

이 맥에서 쓸 수 있나

제 Mac은 Mac Studio(Apple M5 Max, 메모리 48GB, macOS 27.0.1)입니다. 로컬 AI 모델 서버가 메모리를 늘 약 34GB 차지하고 있습니다.

fsearch README에 나온 실측치는 M4 Mac mini에서 잰 값입니다. 데몬이 상주할 때 쓰는 메모리는 21~35MB이고, 인덱스가 디스크에서 차지하는 크기는 309~600MB입니다(README: Linux/Chromium 소스 트리 기준). 이 맥에서는 따로 재 보지 않았습니다. 수치만 보면 작지만, 이 디스크와 메모리 환경에서 직접 재 보지 않았으니 "부담이 없다"고 말하지는 않겠습니다.

이런 분께

  • macOS에서 파일 찾기나 내용 검색이 느리다고 느끼는 분: 오타를 허용하는 이름 검색과 인덱스로 하는 내용 검색이 이 도구의 핵심입니다.
  • 코딩 에이전트를 쓰면서 "파일 위치 파악" 단계를 더 정확하게 만들고 싶은 분: MCP 서버를 그대로 붙여 쓸 수 있습니다.

맞지 않는 분: 윈도우·리눅스 사용자(README에 따르면 macOS 전용), 데몬을 늘 띄워 두기가 부담스러운 환경.

주의할 점

  • 바이너리를 쓰려면 설치와 네트워크가 필요합니다. 릴리스 tarball을 받아 설치하거나 Rust 도구체인으로 직접 빌드해야 합니다. 둘 다 이번 시험 범위 밖이라 직접 해 보지 못했습니다.
  • install --login으로 데몬을 로그인 항목에 등록하려면 시스템 설정에서 Full Disk Access를 직접 승인해야 합니다. 다시 빌드할 때마다 승인도 다시 해야 합니다. 승인하지 않고 쓰면 Desktop, Documents 같은 보호 폴더는 자동으로 건너뜁니다.
  • 디스크를 계속 크롤링하고 FSEvents(파일 변경을 알려 주는 macOS 시스템 기능)를 추적하는 일은 상주 프로세스가 맡습니다. 전력 소모나 보안에 어떤 영향이 있는지는 재 보지 않았습니다.
