rea-video: 영상 받아서 돌려보니 — 핵심 분해까지 통째로 동작했다

2026년 11월 10일 · 읽는 데 7분
한 줄 요약임의의 영상을 받아 샷 단위로 쪼개고, "실사였나, AI 생성이었나, 코드로 그렸나"를 메타데이터·프레임 분석으로 판단해 리포트로 만들어 주는 오픈소스 CLI 도구다. 이번엔 이 맥의 격리 폴더 안에 venv로 설치해 핵심 분해(decompose)를 실제로 돌려 봤다. 합성 쇼츠 영상 2개를 5샷씩 전부 정상 분해했고, 화면에 찍힌 숫자를 OCR로 읽어 변조본을 잡아냈다.
▶
60초 영상으로 보기유튜브 커밋 한 모금 쇼츠

무엇인가

rea-video(저자 JuneYaooo, GitHub에서 5379스타, Apache-2.0)는 영상을 입력받으면 다음 순서로 분석한다.

  1. 샷 분할 — 영상에서 컷이 갈리는 지점을 찾는다.
  2. 근거 수집 — 프레임 리듬, 센서 노이즈(실사 카메라 영상 특유의 미세한 잡음), 화면이 평면인지 여부, AIGC(생성 AI) 메타태그, 음악 BPM(분당 박자 수)·음계, 자막·컷 흔적 등을 기계적으로 모은다.
  3. 판단 — 각 샷을 실사 / AI 생성 / 코드 렌더링 / 스크린 녹화 / 혼합으로 분류한다.
  4. 리메이크 계획 — 각 샷에 촬영 계획·프롬프트를 붙이고, 결과물은 HTML 리포트로 만든다.

"어떻게 만들었는지" 판정 정확도는 README에 이렇게 적혀 있다. 원본 파일 기준으로 오프라인 도구만 쓰면 98.3~99.6%, 플랫폼에서 다시 압축한 영상은 88.6%다. 재인코딩으로 노이즈 근거가 사라지기 때문이다. 여기에 VLM(이미지·영상을 이해하는 모델)이나 에이전트 눈 검시를 더하면 99.6~100%까지 회복된다고 한다. 이 숫자는 저장소 안의 재현 절차 문서에서 가져온 값이고, 이번에 다시 측정하지는 않았다.

영상을 재제작(리메이크)하는 일은 별도 저장소(capsule-cinema)가 맡고, rea-video는 그 앞단의 분석만 한다. 에이전트가 실행하도록 설계되어 있고(README 배지에 "runs in Claude Code | Codex" 표기), 서브커맨드로는 decompose(분해)·probe(정보 조회)·summary(요약)·review(검토) 등이 있다.

직접 해 본 것

저장소(88.3MB)를 이 맥에 내려받고 격리 폴더에 venv를 만든 다음, pyproject의 의존성 5종(numpy, opencv-python-headless, Pillow, PyYAML, onnxruntime)을 모두 설치했다. 그리고 실제 명령을 실행해 결과를 기록했다. ffmpeg는 이미 깔려 있었고, 이번에 새로 설치한 것은 venv 의존성뿐이다.

핵심: 합성 쇼츠 2개 분해. scratch/make_video.py로 SCENES.json 스토리보드(5샷)에서 합성 쇼츠 2개를 만들었다. 하나는 정상본 good.mp4, 다른 하나는 화면 숫자를 27.3에서 72.3으로 바꾼 bad.mp4다. 둘 다 rea_video decompose --no-stems --no-packaging --no-vlm으로 돌렸다. 종료 코드는 모두 0(각각 21.8초)이었고 5샷을 전부 감지했다. 출력은 다음과 같다.

00:51:58 INFO video bad.mp4 540x960 24.00fps 17.50s
00:51:58 INFO detected 5 shots
00:52:00 INFO shot_001 00:00.000-00:02.500 det=code_render(86%) frozen
00:52:01 INFO shot_002 00:02.500-00:10.000 det=code_render(93%) mostly_static
00:52:02 INFO shot_003 00:10.000-00:12.500 det=code_render(86%) frozen
00:52:03 INFO shot_004 00:12.500-00:15.000 det=code_render(86%) frozen
00:52:03 INFO shot_005 00:15.000-00:17.500 det=code_render(74%) frozen
00:52:03 INFO done in 5.4s -> scratch/out/bad

샷마다 74~93% 신뢰도로 코드 렌더링 영상이라고 판단했고, good/bad 각각의 breakdown.json도 정상적으로 생성됐다.

화면 숫자 대조. 같은 실행에서 OCR로 화면의 숫자를 읽어 대본의 숫자(27.3)와 맞춰 봤다. 재현율은 기준인 75%를 충족했고, 변조본(72.3)도 그대로 잡아냈다. 이 보고서를 우리 로컬 모델(Qwen3.8-27B-4bit)에 넘기자 수리 지시가 한 문장으로 돌아왔다(3.1초, 종료 코드 0).

화면에 표시된 72.3을 대본의 27.3으로 수정해야 한다.

stems 모델 다운로드. stems(오디오 분리)를 쓰려면 onnx 모델(67MB)을 내려받아야 한다. 격리 환경에서는 이 다운로드가 막혔다(실행 로그: downloading face model … <urlopen error [Errno 1] Operation not permitted>). face 검출은 Haar 폴백을 쓰거나 건너뛰었다. 그래도 도구는 경고만 남기고 나머지 파이프라인을 정상 완료(종료 코드 0)했다.

안 돌려 본 것. review/apply-review(에이전트 눈 재검시)·correct·tiles·VLM 경로는 이번에 돌리지 않아서 실측 결과가 없다. 도구의 메모리·CPU 부담도 이번 실행에서는 기록하지 않았다.

이 맥에서 쓸 수 있나

환경은 Mac Studio, Apple M5 Max(arm64), 메모리 48GB, macOS 27.0.1(빌드 26A434), 디스크 여유 약 131GB다. 로컬 AI 모델 서버(Splash 1.2.0)가 메모리를 약 34GB 상시 사용한다.

이 환경에서는 venv 의존성 5종과 ffmpeg만 갖추면 decompose까지 모두 돌릴 수 있었다. stems는 모델(67MB) 다운로드가 필요한데, 이번 격리 실행에서는 그 다운로드가 막혔다.

메모리에 여유가 있는지는 확인하지 못했다. README와 저장소 어디에도 요구 사양이 없어 비교할 기준이 없었고, 이번 실행에서 실제 점유량도 기록하지 않았기 때문이다. 다만 모델 서버가 이미 메모리 약 34GB를 쓰고 있어서, 48GB에서 무거운 CV 파이프라인을 함께 돌릴 여지가 있는지는 확인하지 못했다. CPU·GPU 부담도 마찬가지다.

  • 리메이크(재제작)까지 원하는 분 — 별도 저장소(capsule-cinema)가 필요하고 유료 모델을 호출한다

주의할 점

  1. 의존성을 설치하면 제3자 영상 파일을 읽게 된다. ffmpeg 파이프와 오픈소스 CV 코드가 임의의 영상 파일을 열기 때문에, 출처가 불분명한 파일을 돌리기 전에 저장소의 보안 테스트 파일(tests/test_security.py)을 먼저 살펴보길 권한다(이번 실험에서는 돌려 보지 않았다).
  2. 정확도 숫자는 원본 파일 기준이다. 98.3~99.6%는 원본 파일에서의 값이고, 플랫폼에서 재인코딩한 영상은 88.6%로 떨어진다. 에이전트 눈 재검시 단계를 반드시 뒤따라야 한다.
  3. 리메이크는 유료다. 리메이크 경로는 유료 모델을 호출하며, README는 dry-run(실제 실행 없이 미리보기)을 먼저 해 보라고 권한다.
  4. 라이선스. Apache-2.0이라 상업적 사용과 재배포가 가능하다. 다만 재배포할 때는 LICENSE 복사, 변경 표시, NOTICE 보존 같은 조건을 지켜야 한다. README FAQ는 남의 영상 재유포 금지, 리메이크는 권리를 가진 소재만 재사용, 게시할 때 AI 표기 규정 준수를 권고한다.
